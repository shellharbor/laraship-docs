## Verified behavior and deliberate restrictions

| User question | Contract |
| --- | --- |
| New or existing application? | New uses Laravel ^13.0 by default; Basic also offers ^12.0 and Advanced accepts X.Y constraints >=12.0. Existing supports HTTPS/SSH/SCP and opt-in HTTP/git/file transports, optional branch and SSH server key path. Existing cannot install Filament/Horizon or set Laravel version. |
| Which presets? | Multiple compatible presets. `admin-panel`: Filament, Redis, queue. `api`: Horizon, automatically Redis, PHP 16M. `staging`: Basic Auth, Redis. admin-panel+staging and api+staging are supported; admin-panel+api is blocked because Queue/Horizon conflict. Modules/auth are additive; explicit upload overrides win. Preset-required features stay locked until the relevant preset is unchecked. |
| What address? | Explicit slug required; format matches CLI, reserved nginxproxy rejected case-insensitively. CLI domain validation only checks allowed characters; wizard deliberately requires a valid multi-label DNS hostname and rejects IP literals. Auto-slug is omitted because CLI prepends it to the domain. |
| Where is the database? | PostgreSQL 17 or MySQL 8.4, container or already running on the same server. Native is not remote/cloud. Native port sets Laravel DB_PORT; database provisioning still uses the host's normal local client connection. |
| Custom database identity? | Names/users: `[A-Za-z0-9_][A-Za-z0-9_-]*`. PostgreSQL both max 63; MySQL name 64/user 32. Container MySQL app user cannot be `root` (native CLI permits it). |
| What about passwords? | No actual password inputs, persistence, telemetry, or remote generation. LaraShip generates them by default. Optional flags produce applicable PostgreSQL/MySQL/Redis/Filament/Auth placeholders. Native MySQL separately requires a marked `<MYSQL_ROOT_PASSWORD>` template. A server-local hidden-input helper supports all placeholders, while disclosing process-argument exposure. |
| Which ports? | 1–65535, optional. Project ports 80/443 reserved for shared proxy. Wizard rejects duplicates including explicitly chosen native DB port (stricter than CLI). All project bindings are loopback by default. Redis port remains relevant without its module because Redis container is in the base stack. |
| Backups? | `backup` creates DB dumps at startup and daily, retained 1–3650 days (default 7). `--create-backup` is a separate ZIP without database volume contents or certificates. |
| Custom PHP upload? | CLI syntax `[0-9]+[KMGkmg]?` (including 0). Omitted values preserve PHP defaults 2M/8M, or preset 16M. |
| Notifications? | Final completion supports a trusted script and/or HTTPS POST, password omission by default, explicit optional application-secret inclusion, token-file paths and bounded timeouts. Legacy credential PUT remains separate. Explicit allow-insecure-endpoint plus acknowledgement permits HTTP for both APIs; target trust is still required. Browser contacts neither API. |
| Run a hook? | Application post-deploy: Expert opt-in, one line, acknowledgement of arbitrary PHP-container code execution and repetition during updates. Applies to New and Existing. |
| Export config? | KEY=VALUE with matching outer quotes and placeholder-only passwords; never shell-source. CLI presets → config lines (PRESET at its position) → ordinary CLI; true booleans/modules add and empty scalar values are skipped. Protect local file using chmod 600. Any secret template remains visibly incomplete. |
| How is LaraShip installed/run? | Visible guide offers the pinned Bash toolkit, digest-pinned Docker CLI and Python CLI with native/Docker backends. The same validated deployment options/config apply to all. Docker server operations need local socket, host network and identical paths; native DB provisioning uses Bash or Python native. |

## Source discrepancies resolved

- README says explicit ports are not checked for occupancy; current runtime checks availability before deployment. Browser promises neither occupancy nor infrastructure validation.
- Examples still mention MySQL 8.0 and older password limitations. `versions.env` selects MySQL 8.4, and actual credential validation/encoding governs supported characters.
- CLI only requires nonempty email strings; wizard uses an email format check.
- CLI accepts HTTP, git:// and file:// repositories; the public wizard supports them behind an Advanced opt-in and rejects credentials, query strings, fragments, whitespace and controls. Local repository paths join read-only Docker inputs.
- Redis module wires Laravel to an already present Redis service; it is not the switch that creates that container.
- DH parameters affect project nginx, not the shared TLS proxy. Horizon requires a production authorization gate.
- Upstream pre-parses `--config`, `--preset`, `--dry-run` and its early exit actions without respecting argument value positions. The wizard rejects those exact strings as free-text values; quoting alone cannot fix this parser behavior.

## Multiple-preset contract

Source `main` handles every `--preset NAME` in order; `read_config_file` also loads every `PRESET=NAME` line. The wizard emits repeated flags/keys rather than a comma-separated preset value. Selection is a deduplicated array in registry order: admin-panel, api, staging. Current compatible combinations have no competing scalar defaults; the effective merge uses the last nonempty preset upload value in registry order, then the user's explicit override. Modules and enabled booleans remain additive.

`presetBlock` considers both selected presets and manual modules. Queue worker and Horizon cannot coexist; new-only presets are unavailable for existing repositories. Selected checkboxes stay removable. `togglePreset` guards selection even when called outside the control, and `validate` independently rejects conflicting/source-incompatible preset sets at step 0 before generating Bash or Docker commands. Unknown names are rejected. Switching source to Existing retains staging and removes only new-only presets/modules.

Preferences retain the v1 storage key. A valid legacy single `preset` becomes an array; a new array takes precedence, including an empty array. Restoration filters unknown/duplicate names, then accepts a compatible subset in registry order after manual services/source are restored. A malformed admin-panel/api combination keeps the first allowed preset, with staging retained if present. No new identity fields enter persistence. Clearing presets does not erase separately chosen services.

## Installation and verification boundary

The installation guide precedes the wizard and is also accessible in the result. It explains that LaraShip is a server CLI, the site generates commands locally, and application services use Docker with all runners. The runner preference lives in App memory, outside deployment settings/storage. Both English and Russian are supported.

**Bash:** clone the entire official repository into a previously absent `/opt/laraship`, then check out the pinned commit. No guessed release URL or `curl | bash` is used. Review the toolkit before running it as root. Required: Ubuntu 20.04+, sudo, Git, Python 3, curl, ss, flock, pgrep, timeout; Docker Compose V2 if Docker is already installed; reachable DNS/80/443 and package registries. The script can install Docker when absent. The guide includes package and full-checkout commands.

**Docker:** verified [Docker Hub image](https://hub.docker.com/r/shellharbor/laraship) `shellharbor/laraship:1.3.0`, index digest `sha256:af97f0378afc5bd911a39d3af34b0a73836ccd1b4d4c052d552a643334fd1eca`, manifest `sha256:387d5bd00b316c3b372139749e5e316165ade4c1eff2b10bcd6b2e007cd06a13`, platform `linux/amd64`. Docker Hub API metadata was checked on 2026-10-22. OCI source revision is `4dfec97ae4c227fe35cf84f5ac5b5e65b18a1c30`, version 1.3.0, matching the website's source pin. SHA256 comparisons verified deployment/version files, all six lifecycle scripts, Kubernetes wrapper/renderer, five lib helpers, all five modules, all three presets, preflight and entrypoint against the source pin. This establishes the audited Compose CLI contracts; it is not an audit of every image layer or a real Kubernetes rollout.

The host needs an installed/running Docker Engine on a supported Ubuntu version; the guide links [Docker's official repository installation](https://docs.docker.com/engine/install/ubuntu/) and gives 24.04 LTS as an example. Docker's current supported release list is narrower than LaraShip's 20.04 minimum. The CLI image contains Docker client and Compose plugin. Source checkout is optional. Image pull, version, help and a sample dry-run appear before deployment-directory preparation.

The generated deployment command follows the pinned [container contract](https://github.com/shellharbor/laraship/blob/4dfec97ae4c227fe35cf84f5ac5b5e65b18a1c30/docs/CONTAINERS.md): host networking and writable same-path binds for `/var/run/docker.sock`, `/var/www`, `/run/lock/laraship` and `/var/backups/laraship`. The guide includes upstream directory preparation and explains socket administrative access and trusted images. No privileged flag, custom hostname, remote daemon or Docker Desktop production path translation is offered. A config/SSH key is read-only at the same absolute path. Docker's CSV mount grammar and POSIX shell quoting are handled separately.

Informational containers need no host socket/network/deployment directories; an optional deploy-key file still needs its read-only mount because the CLI checks existence during dry-run. Native DB provisioning is rejected by the container adapter outside dry-run. Results resolve direct Docker/native selections to Bash and Python Docker/native selections to Python native, disable Docker options with an explanation and retain the user's preferred runner if they return to a container database. A direct invalid Docker/native generation call also throws. Management uses the image's list/update/backup/activate/deactivate/remove aliases with server mounts.

One-time ZIP location: Bash `/tmp`; Docker `/var/backups/laraship` via image `LARASHIP_ARCHIVE_DIR`. The CLI's dry-run prose still says `/tmp` in container mode; runtime archive code and Dockerfile determine the effective location. The site shows the correct runner-dependent directory. Database dumps remain separate.

No application deployment or Docker image build belongs to this static website's runtime. The downloaded source is an ignored read-only fixture. No upstream build inputs were changed, so no image rebuild is needed. Optional Docker tests use the already cached immutable image with no network, server socket or writable deployment mounts. They check informational entrypoints, synthetic read-only config/key fixtures, CLI dry-runs, audited file hashes, extracted lifecycle parsers and offline Kubernetes rendering; Compose is validated without starting services. Full provisioning on a Linux server, server mounts/preflight in production, Git/DNS/ACME, real DB operations and cluster rollout remain unverified.

When updating source or image pins: re-audit these files plus Dockerfile, docker/entrypoint.sh, docker-preflight.py and docs/CONTAINERS.md. Verify registry platforms/digest, OCI labels and affected image/source contracts. Update registry/constraints/validation as needed, regenerate the CLI reference after registry changes, then run unit, upstream differential, explicit Docker integration, UI/accessibility and Pages-base checks. Never silently follow upstream main or a mutable tag in production commands.

## Python CLI and completion contract (1.3.0)

Python is a dependency-free Python 3.10+ CLI adapter, not an application backend. Audited files: docs/PYTHON.md, pyproject.toml, src/laraship/{cli,install,__init__,__main__}.py; the native installer performs bounded HTTPS downloads, SHA-256 verification, safe extraction and refuses existing targets. The wizard uses its native default directory explicitly and selects Docker by immutable image digest. Native DBs retain native execution. Adapter options/mounts precede --; forwarded flags follow it. Python Docker's raw CSV mount grammar cannot encode commas/double quotes reliably; runner-specific validation blocks those paths and .. while direct Docker retains proper CSV quoting. Privileged commands resolve the executable through command -v before sudo changes PATH.

PyPI version 1.3.0 was available on 2026-10-22. Published wheel laraship-1.3.0-py3-none-any.whl SHA256: 316c80b0b801658e091fe0d57277d3961ab964649c50d47fed35125f85cda8db. Download hash and all four adapter Python files matched audited source; the unpacked published wheel returned laraship 1.3.0 in the offline CLI container. This does not establish a fresh pipx installation or production Linux deployment.

Completion audit inputs: lib/completion.{sh,py}, deploy-laravel.sh validation/arming/finalization, lib/endpoint.py, docs/COMPLETION.md, examples/hooks/completion.sh and upstream completion tests. Advanced UI supports both targets with separate trust acknowledgements, HTTPS by default and explicit HTTP opt-in, timeout 1–300, token-file paths only and password inclusion off by default. Explicit inclusion applies to both reports; root DB secrets/API tokens/SSH keys/.env remain excluded. All completion fields/consents are excluded from preference persistence and ignored by generation when disabled.

Hooks receive final version-1 JSON on stdin; APIs receive POST with Idempotency-Key: run_id. Targets cover success, operational failure or handled HUP/INT/TERM after full validation arms completion. Delivery follows archive creation when reached and lock release; original exit status survives callback failure. Each target gets one bounded attempt. Dry-run/help/invalid settings and early root/toolkit loading failures do not deliver; SIGKILL/power loss cannot finalize. Only deployment is covered. --post-deploy and the legacy credential --endpoint keep their old execution/PUT semantics.

File existence, invoking-user ownership, executable/private modes and trusted real parent directories are enforced by the engine. Browser validation checks absolute paths without . or .., not filesystem facts. Sudo deployment normally needs root-owned hook/token files; root-only files also need sudo validation. Docker runs hooks inside its CLI container and mounts script/token/key/config inputs read-only at identical paths, including inspection. Password-bearing reports need private receiver storage; a failed deployment's known credentials/readiness fields may be unverified.
